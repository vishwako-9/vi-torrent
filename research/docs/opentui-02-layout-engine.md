# Layout Engine

## Purpose
opentui's flexbox layout is a thin TypeScript FFI wrapper around the native Zig-hosted Yoga engine (the same layout library React Native uses). This is the direct analogue of Textual's CSS layout system — it decides every widget's x/y/width/height each frame — but exposed as an imperative flexbox API instead of a stylesheet language.

## Key files
- `packages/core/src/yoga.ts` (1146 lines) — the full Yoga binding: `Config`, `Node` classes, and every layout enum (`Align`, `FlexDirection`, `Justify`, `Overflow`, `PositionType`, `Edge`, `Unit`, etc.), exported as a default `Yoga` namespace object.
- `packages/core/src/types.ts` — shared cross-cutting types: `RenderContext` interface (the contract every `Renderable` renders against), `TerminalCapabilities`, `TextAttributes` bit flags, `CapturedFrame`/`CapturedLine`/`CapturedSpan` (frame introspection for tests/snapshots), `LineInfo`/`LineInfoProvider` (text-wrap line metadata used by text-buffer views).

## How it works
`Yoga.Node` wraps a native pointer (`ptr: Pointer`) with a `nodeRegistry: Map<Pointer, Node>` so the same JS wrapper is reused for a given native node. Construction: `Node.create(config?)`, or opentui's own `Node.createForOpenTUI()` (used by every `Renderable` — see `Renderable.ts` constructor: `this.yogaNode = Yoga.Node.createForOpenTUI()`). Tree ops are `insertChild(child, index)`, `removeChild()`, `removeAllChildren()`, `getChild(index)`, `getChildCount()`, `getParent()`. Layout is computed via `calculateLayout(width?, height?, direction = Direction.LTR)` and read back via `getComputedLayout(): Layout` (`{left, right, top, bottom, width, height}`) or the individual `getComputedWidth()`/`getComputedTop()`/etc. accessors, plus `getComputedMargin/Padding/Border(edge)`.

Styling setters mirror CSS flexbox 1:1: `setFlexDirection`, `setJustifyContent`, `setAlignItems`/`setAlignSelf`/`setAlignContent`, `setFlexWrap`, `setFlex`/`setFlexGrow`/`setFlexShrink`/`setFlexBasis`, `setWidth`/`setHeight`/`setMinWidth`/`setMaxWidth`/etc. (accepting `number | "auto" | "N%" | Value`), `setMargin`/`setPadding`/`setPosition` (each keyed by an `Edge` enum: `Left/Top/Right/Bottom/Start/End/Horizontal/Vertical/All`), `setGap(gutter, value)`, `setBorder(edge, width)`, and `setOverflow`/`setDisplay`/`setPositionType` (`Static/Relative/Absolute`). Enum values match Yoga's real C API numbering (e.g. `FlexDirection.Row = 2`, `Overflow.Scroll = 2`). There's also custom-measure support: `setMeasureFunc(fn: (width, widthMode, height, heightMode) => {width,height})` and `setDirtiedFunc(fn)`, routed through one shared native FFI callback per loaded library (`ensureMeasureCallback`/`ensureDirtiedCallback`) rather than one callback per node — a real perf-motivated detail worth knowing if we ever hit many nodes with custom measurement (e.g. auto-sizing text cells).

`Renderable.ts`'s `LayoutOptions` (see doc 01) is the ergonomic, string/percent-friendly surface (`flexGrow`, `flexDirection: FlexDirectionString`, `margin: number | "auto" | "N%"`, etc.) that gets translated into these raw Yoga `Node` calls via helper parsers in `./lib/yoga.options.js` (`parseFlexDirection`, `parseAlign`, `parseJustify`, `parseOverflow`, `parsePositionType`, `parseWrap`) — so application code never touches `yoga.ts` directly; it sets plain-string/number properties on a `Renderable` (or JSX props in the Solid package) and the base class does the Yoga marshaling.

`types.ts`'s `RenderContext` is the interface every `Renderable` holds a reference to (`this._ctx`) — it's what `CliRenderer` implements (doc 01) and is also stubbed out by `ScrollbackSnapshotRenderContext` for scrollback rendering. It carries hit-testing (`addToHitGrid`), focus (`focusRenderable`/`currentFocusedRenderable`), selection (`getSelection`/`startSelection`/`updateSelection`), cursor control, and `frameId` (monotonic per-frame counter for cheap per-frame memoization in widgets). `TextAttributes` defines the bitmask used for bold/dim/italic/underline/blink/inverse/hidden/strikethrough — consumed by `OptimizedBuffer.setCell`'s `attributes` parameter and by text-buffer spans (doc 03).

## Relevance to our torrent client rebuild
This replaces Textual's CSS (`DEFAULT_CSS` strings like `align: center middle; width: 70%; border: round $accent`) with equivalent imperative flexbox calls set as `Renderable`/JSX props — e.g. our current `InputModal`'s `#dialog { width: 70%; height: auto; }` becomes a `Box` (doc 04) with `width: "70%"`, `height: "auto"`. The main torrent table's column layout and the settings-modal's stacked label/input rows are both straightforward flex-column/flex-row trees — no bespoke table-layout code needed beyond what `TextTable` (doc 06) already provides. One thing to plan for explicitly: Textual's CSS gives us `align: center middle` as one declarative line for centering modals; here we'd compose `justifyContent`/`alignItems: "center"` on a full-screen wrapping `Box` the same way a web flexbox centers a modal — same effect, one extra wrapper node instead of a CSS selector.
