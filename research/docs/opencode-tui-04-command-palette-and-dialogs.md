# Command Palette and Dialogs

## Purpose
This is the single most relevant subsystem for our rebuild: a fuzzy-searchable command palette that both a global keybind (`ctrl+p`) and every `/slash` command in the prompt route through, plus ~10 concrete dialog screens (session list, model picker, provider connect, theme picker, etc.) all built on one shared list-selection primitive.

## Key files
- `component/dialog-command.tsx` — `CommandProvider`/`useCommandDialog`: the command registry, keybind dispatch, and the actual palette dialog.
- `component/dialog-agent.tsx`, `dialog-mcp.tsx`, `dialog-model.tsx`, `dialog-provider.tsx`, `dialog-session-list.tsx`, `dialog-session-rename.tsx`, `dialog-skill.tsx`, `dialog-stash.tsx`, `dialog-tag.tsx`, `dialog-theme-list.tsx` — concrete dialogs, all thin wrappers around `DialogSelect`/`DialogPrompt` (doc 05).
- `component/dialog-status.tsx` — a status/info dialog (not in the original file list but present in the repo; read for completeness) showing MCP/LSP/formatter/plugin counts.

## How it works
There is **no bespoke fuzzy-matching implementation** in `dialog-command.tsx` itself — all matching lives in `ui/dialog-select.tsx` (doc 05) via the `fuzzysort` npm package, called as `fuzzysort.go(needle, options, { keys: ["title", "category"], scoreFn: (r) => r[0].score * 2 + r[1].score })`, i.e. title matches are weighted 2x over category matches. `dialog-command.tsx` itself is a thin registry + dispatcher:

`CommandProvider` renders nothing visible; it holds a `createSignal<Accessor<CommandOption[]>[]>` array of *registration functions* (not flat option lists) — every component that calls `command.register(() => [...])` (theirs do this in `app.tsx`, `home.tsx`, `routes/session/index.tsx`, `component/prompt/index.tsx`, etc.) pushes a `createMemo`-wrapped callback onto this array and `onCleanup`s its removal, so the merged command set is always exactly "whatever screens/components are currently mounted" — a session-scoped command like "Fork from message" simply doesn't exist while on the home screen, no manual enable/disable bookkeeping needed. `entries()` is a `createMemo` that flattens all registrations and attaches a `footer` (the keybind's printed form) if the option declares one. `CommandOption` extends `DialogSelectOption` with: `keybind` (a config key, resolved via `useKeybind().print()`), `suggested` (surfaced in a synthetic "Suggested" category at the top when the palette opens with no typed query), `slash: {name, aliases}` (makes it reachable as `/name` or `/alias` in the prompt's autocomplete — see doc 06), `hidden` (exists for keybind dispatch / `trigger()` but never shown in the palette list, used for things like scroll commands), and `enabled` (conditionally greyed out/excluded).

Global keybind dispatch happens in a `useKeyboard()` inside `CommandProvider` that checks every registered option's `option.keybind` against the pressed key via `keybind.match()` and calls `onSelect` directly — bypassing the dialog UI entirely for keybind-triggered commands. A separate `useKeyboard()` opens the palette itself on the `command_list` keybind. `trigger(name)` (used by slash commands and `TuiEvent.CommandExecute`) looks up an option by `value` and calls its `onSelect`. `keybinds(enabled: boolean)` is a suspend/resume counter — the autocomplete dropdown (doc 06) calls `command.keybinds(false)` while open so command keybinds don't fire while the user is typing a filename.

`DialogCommand` (the actual rendered palette) is ~10 lines: it renders `<DialogSelect title="Commands" options={list()} />` where `list()` prepends the suggested-options subset only when the user hasn't typed a filter yet (`ref?.filter` check) — after that it's just the plain flat option list, letting `DialogSelect`'s own category-grouping (doc 05) organize by `category: "Session"|"Agent"|"Provider"|"System"` etc.

The concrete dialogs are uniformly thin: `DialogAgent`/`DialogMcp`/`DialogSessionList`/`DialogThemeList` all just map some `sync.data.*` array into `DialogSelectOption[]` and pass to `<DialogSelect>`, with dialog-specific extras layered on top of the shared primitive rather than reimplemented — e.g. `DialogMcp` adds a `keybind={[{keybind: "space", onTrigger: toggle}]}` for space-to-toggle-enabled; `DialogSessionList` adds delete/rename keybinds with a "press again to confirm" two-step (tracked via a local `toDelete` signal, not a separate confirm dialog) and server-side search via `createResource` + a 150ms debounced signal (`createDebouncedSignal`, doc 08); `DialogModel` is the most complex — it merges favorites/recents/all-provider-models into grouped sections when unfiltered, but flattens to a single fuzzysort pass across providers+popular-providers when the user types (`flat={true} skipFilter={true}` on `DialogSelect`, doing its own filtering via `onFilter`+`fuzzysort.go` rather than delegating to `DialogSelect`'s built-in filter, because it needs the favorites/recents-exclusion logic first); `DialogProvider` drives a 3-step OAuth-or-API-key flow (`createDialogProviderOptions()` is exported standalone so `DialogModel` can also open it via a keybind).

## Relevance to our torrent client rebuild
This is the direct blueprint for our slash-triggered command palette. **Copy the registration pattern wholesale**: a `CommandProvider` where any mounted component (main table view, a modal, whatever) calls `command.register(() => [...])`, so our 11 commands (add-magnet, settings, peers, etc.) are declared next to the component that owns them instead of in one central list — this also gives us screen-scoped commands for free later (e.g. a "Remove torrent" command that only exists when a row is selected). **Pull in `fuzzysort`** (it's a small, dependency-free npm package) rather than hand-rolling fuzzy matching — their title-weighted-2x-over-category scoring is a good starting default. Give each command an optional `slash: {name, aliases}` exactly like theirs so the same registration serves both the `ctrl+p`-opened palette and direct `/add-magnet` typing (see doc 06 for how the prompt box routes `/name` to `command.trigger`). Their `hidden: true` pattern (registered for keybind/trigger purposes but invisible in the palette) is useful for scroll/navigation commands we might add later. For dialogs specifically: our `SettingsModal`/`TorrentLimitModal`/`PeerModal` should each be a thin wrapper around one shared `DialogSelect`-equivalent (doc 05) rather than bespoke list UIs — `DialogMcp`'s space-to-toggle and `DialogSessionList`'s press-again-to-confirm-delete are both directly reusable idioms for, respectively, toggling a torrent's paused state and confirming torrent removal.
