# Dialog UI Primitives

## Purpose
This is the generic, reusable modal layer everything in doc 04 is built from: one stack-based dialog host, one fuzzy-searchable list-selection component (`DialogSelect`) that does almost all the heavy lifting, a handful of single-purpose prompt/confirm/alert dialogs, a toast notification system, and small helpers (link, spinner-color-generator).

## Key files
- `ui/dialog.tsx` — `DialogProvider`/`useDialog`: the modal stack (push/replace/clear), the visual chrome (centered box, dim overlay), Escape/Ctrl+C-to-close.
- `ui/dialog-select.tsx` — `DialogSelect`: the fuzzy-searchable, categorized, keyboard+mouse-navigable list. Used by nearly every dialog in doc 04.
- `ui/dialog-alert.tsx`, `dialog-confirm.tsx`, `dialog-prompt.tsx` — single-button-ack, two-button confirm, single-textarea-input dialogs. Each exposes a `.show(dialog, ...)` static method returning a `Promise`.
- `ui/dialog-help.tsx` — static one-screen help dialog.
- `ui/dialog-export-options.tsx` — a checkbox-group + filename-textarea dialog (session export options).
- `ui/link.tsx` — clickable text that opens a URL via the `open` package.
- `ui/spinner.ts` — Knight-Rider-style animated color-gradient generator for the opentui `<spinner>` widget (not a component itself — a `ColorGenerator` factory).
- `ui/toast.tsx` — `ToastProvider`/`useToast`/`<Toast/>`: single-slot, auto-dismissing notification.

## How it works
`DialogProvider`'s state is a `createStore({ stack: [], size: "medium"|"large" })`. Despite the name "stack," in practice `replace()` (used everywhere) clears the whole stack and pushes one entry — true nesting (`push` without clearing) isn't exposed as a public API, only `replace`/`clear`. Each stack entry is `{ element: JSX.Element, onClose?: () => void }`. A global `useKeyboard()` closes the top entry on Escape or Ctrl+C (unless there's an active text selection, so copy-via-selection isn't accidentally eaten) and calls `refocus()` — a `setTimeout(1)` that walks the render tree to confirm the previously-focused element still exists before refocusing it (defensive against the focused element having been unmounted while the dialog was open). Only the **top** of the stack is ever rendered (`value.stack.at(-1)!.element`). Visual chrome (`Dialog` component) is a full-screen absolutely-positioned dim overlay (`RGBA.fromInts(0,0,0,150)`) with a centered fixed-width box (`60` or `80` cols via `size`), dismissible by clicking the overlay (guarded against dismissing when the click was actually a text-selection drag).

`DialogSelect<T>` is the single most reused component in the whole app. Props: `title`, `options: DialogSelectOption<T>[]` (`{title, value, description?, footer?, category?, disabled?, bg?, gutter?, onSelect?}`), `flat?` (skip category grouping once filtering), `skipFilter?` (caller does its own filtering, e.g. `DialogModel`), `onFilter`/`onSelect`/`onMove` callbacks, `current?` (pre-selects and highlights a value with a `●` marker), and an optional `keybind` array for dialog-specific extra actions (space-to-toggle, delete, rename, etc., each declaring its own `title` shown in a footer hint bar). Internally: an `<input>` at the top drives `store.filter`; a `createMemo` runs `fuzzysort.go(needle, options, {keys:["title","category"], scoreFn: r => r[0].score*2 + r[1].score})` when there's a query, otherwise passes options through filtered only by `disabled !== true`. Results are grouped by `category` (`remeda`'s `groupBy`) unless `flat && filter.length > 0`, in which case grouping is skipped so filtered results read as one flat ranked list. Selection state (`store.selected`, an index into the flattened list) drives both keyboard nav (`↑↓`/`ctrl+p`/`ctrl+n`/`PageUp`/`PageDown`/`Home`/`End`) and auto-scroll (`moveTo()` centers on filter-change, edge-scrolls on arrow-key nav). Mouse hover only moves selection if the last input mode was `"mouse"` (tracked to prevent layout-shift-under-cursor from stealing selection during typing — a real bug they clearly hit and fixed). Rows render via a small `Option` sub-component: optional `●` current-marker or custom `gutter` JSX (used for a spinner icon in the session list), truncated title (`Locale.truncate(title, 61)`), optional muted description, optional right-aligned footer.

`DialogAlert`/`DialogConfirm`/`DialogPrompt` are all the same shape: a functional component for inline use, plus a static `.show(dialog, ...args)` method that wraps `dialog.replace(() => <Component .../>, onCloseResolve)` in a `new Promise`, resolving on confirm/cancel/dismiss — this lets *imperative* call sites (`await DialogConfirm.show(dialog, "Confirm Redo", "...")`) exist alongside the declarative JSX form. `DialogConfirm` has left/right arrow-key toggling between two buttons; `DialogPrompt` is a single 3-line `<textarea>` with Enter-to-submit.

`toast.tsx`'s `ToastProvider` holds a single `currentToast | null` (not a queue — a new toast replaces the old one and resets the dismiss timer, `.unref()`'d so it doesn't keep the process alive). `<Toast/>` renders top-right, colored by `theme[variant]` border, auto-dismissing after `duration` (default 5000ms, parsed/defaulted via the same zod schema as `TuiEvent.ToastShow`).

`ui/spinner.ts` is unrelated to dialogs structurally but colocated here — it's a parameterized "Knight Rider" scanning-gradient color generator (`createColors`/`createFrames`) consumed by the opentui `<spinner>` widget wherever an agent-colored loading indicator is shown (prompt status bar, block-tool spinners).

## Relevance to our torrent client rebuild
**`DialogSelect` is the one component to port almost verbatim** — it directly replaces bespoke list-rendering in our `PeerModal`/`FileModal`/`TorrentLimitModal`, and gives us fuzzy search, categories, keyboard+mouse nav, and scrolling for free instead of reimplementing per-modal. Our `SettingsModal` likely maps to a `DialogSelect` with `keybind`-driven toggles (à la `DialogMcp`'s space-to-toggle) rather than a bespoke settings form. `DialogProvider`'s single-slot "stack" (really just replace/clear) is simpler than a true modal stack and is probably sufficient for us too — we don't currently have nested-modals-within-modals in `tui.py`, so don't build more than this needs. The `.show()` static-method-returns-Promise pattern is directly useful for a confirm-before-delete-torrent flow (`await DialogConfirm.show(dialog, "Remove torrent?", "...")` reads far better than callback-threading through Textual's current modal push). `toast.tsx`'s single-slot auto-dismiss notification is a good fit for transient events like "torrent added" / "magnet parse failed" — simpler than a queue, and we likely don't need more than one visible at a time either. `ui/spinner.ts` is overkill for us initially (a plain sync spinner suffices for "checking tracker..." states) but is there if we ever want a more polished per-torrent activity indicator.
