# Solid Reconciler (`@opentui/solid`)

## Purpose
A separate package (`packages/solid`, not part of `@opentui/core`) that lets you write opentui UIs as JSX/SolidJS components (`<box>`, `<text>`, etc.) instead of imperatively `new`-ing `Renderable` subclasses and calling `.add()`. It's a SolidJS "universal renderer" (the same low-level mechanism Solid itself provides for targeting non-DOM backends) wired to opentui's `BaseRenderable` tree.

## Key files
- `packages/solid/src/reconciler.ts` (408 lines) — the actual `createRenderer<DomNode>({...})` call: `createElement`, `insertNode`/`removeNode`, `setProperty`, `getParentNode`/`getFirstChild`/`getNextSibling` — every DOM-like operation Solid's compiler output needs, mapped onto opentui's `Renderable`/`TextNodeRenderable` tree.
- `packages/solid/src/elements/catalogue.ts` — `baseComponents`: the JSX tag name → `Renderable` constructor map (`box`→`BoxRenderable`, `text`→`TextRenderable`, etc.), plus `extend()` to register custom tags.
- `packages/solid/src/elements/hooks.ts` — Solid hooks: `useRenderer`, `useKeyboard`, `usePaste`, `useTerminalDimensions`, `onResize`/`onFocus`/`onBlur`, `useTimeline`.
- `packages/solid/src/elements/index.ts` — barrel: re-exports catalogue, hooks, extras (`Portal`, `Dynamic`), and slot.
- `packages/solid/src/elements/extras.ts` — `Portal` (render children elsewhere in the tree, e.g. for modals) and `Dynamic`/`createDynamic` (render a component/tag chosen at runtime).
- `packages/solid/src/elements/slot.ts` (393 lines) — `SlotRenderable`/`TextSlotRenderable`: Solid-specific plumbing so `<Show>`/`<For>`-style conditional/list rendering can swap children in place without the null-child edge cases a naive DOM-like reconciler would hit.
- `packages/solid/src/renderer/index.ts` — thin wrapper around Solid's own `createRenderer` (from `./universal.js`, Solid's public "universal renderer" API), adding `mergeProps`.
- `packages/solid/src/scrollback.ts` (227 lines) — `createScrollbackWriter`-style helpers for rendering a Solid tree into the scrollback surface from `CliRenderer.createScrollbackSurface()` (doc 01) — a separate, less common rendering target from the main screen.
- `packages/solid/src/types/elements.ts` (190 lines) — the big TypeScript mapping of every catalogue tag to its JSX prop type (derived from each `Renderable`'s real constructor options via `ExtractRenderableOptions`), plus `NonStyledProps`/`GetNonStyledProperties` (props excluded from the `style` prop's type per-tag).
- `packages/solid/index.ts` (package root) — `render(node, rendererOrConfig)`: the actual bootstrap entry point (see below).

## How it works
`reconciler.ts` builds on Solid's universal-renderer contract: `createElement(tagName)` looks up the tag in the component catalogue and constructs `new elements[tagName](solidRenderer, {id})`; `_insertNode`/`_removeNode` translate Solid's DOM-shaped insert/remove calls into `parent.add(node, index)`/`parent.remove(node)` on the underlying `BaseRenderable` tree, with special-casing for `TextNode` (must be inside a `<text>` or another text node — "Orphan text error" is thrown otherwise), `SlotRenderable` (Solid's conditional-rendering placeholder, swapped for its real child on insert), and `ScrollBoxRenderable` (whose real children live three levels down inside `wrapper→viewport→content`, so `getParentNode` walks back up to present the `ScrollBoxRenderable` itself as the logical parent). `setProperty(node, name, value, prev)` is the JSX-prop-to-Renderable-API mapping layer: `on:eventName` props call `node.on/off`, `style` merges into text attributes/fg/bg for text nodes or spreads each key as a direct property assignment for other renderables, and several props get special event wiring (`onChange`→`SelectRenderableEvents.SELECTION_CHANGED`/`TabSelectRenderableEvents...`/`InputRenderableEvents.CHANGE` depending on node type, `onInput`→`InputRenderableEvents.INPUT`, `onSubmit`→`InputRenderableEvents.ENTER`, `onSelect`→`ITEM_SELECTED`) — this is the file to read if a JSX prop doesn't seem to do what you expect.

`elements/catalogue.ts`'s `baseComponents` map is the actual JSX vocabulary: `box`, `text`, `input`, `select`, `textarea`, `ascii_font`, `tab_select`, `scrollbox`, `code`, `diff`, `line_number`, `markdown`, plus text-span tags `span`/`b`/`strong`/`i`/`em`/`u`/`br`/`a` (each a `TextNodeRenderable` subclass — `b`/`strong` set `TextAttributes.BOLD`, etc., `a` sets `link: {url: href}`). **Notably absent from this catalogue: `TextTable` and `Slider`** — those two `@opentui/core` renderables (docs 05/06) have no built-in JSX tag in this version; using them from Solid would require `extend({ table: TextTableRenderable })` (the documented extension mechanism) rather than a tag opentui ships out of the box — a concrete, real gap worth confirming isn't fixed in a newer solid-package version before we commit to table rendering strategy.

Bootstrapping (from `packages/solid/index.ts` and the package README): `render(() => <text>Hello, World!</text>)` is the entire entry point — it internally calls `createCliRenderer(config)` (doc 01) if not given an existing `CliRenderer`, attaches Solid's animation `engine`, wraps your root component in a `RendererContext.Provider`, and calls Solid's own `_render` (from `reconciler.ts`) with `renderer.root` (the `CliRenderer`'s `RootRenderable`, doc 01) as the mount target. Project setup per the README: `tsconfig.json` needs `"jsx": "preserve"`, `"jsxImportSource": "@opentui/solid"`; `bunfig.toml` needs `preload = ["@opentui/solid/preload"]`; then `bun index.tsx` with `import { render } from "@opentui/solid"; render(() => <text>Hello, World!</text>)`. Building for distribution uses `Bun.build` with `@opentui/solid/bun-plugin` (this is a different, JSX-transform bun-plugin than doc 09's runtime-module plugin).

**Version gap**: this cloned repo is `@opentui/core`/`@opentui/solid` **0.4.5**; the sibling `codemie-opencode-src` project (a real, shipping Solid+opentui TUI a parallel agent is studying) pins `@opentui/core: "0.1.79"` and `@opentui/solid: "0.1.79"` in its `package.json` — a genuine 20+ patch-version gap. Spot-checking codemie's actual component files (`app.tsx`, `component/*.tsx`) shows the same core JSX vocabulary in active use at 0.1.79 — `<box>`, `<text>`, `<span>` with the same lowercase-tag convention and the same `render()`/`useKeyboard`/`useRenderer`/`useTerminalDimensions` import names from `@opentui/solid` — so the basic authoring model has been stable across that gap. This is not a full API diff (no CHANGELOG was consulted here — worth doing before depending on any specific 0.4.5-only API, since our target Windows install will pull whatever is current on npm, likely much closer to 0.4.5 than to 0.1.79).

## Relevance to our torrent client rebuild
If we choose the Solid path (versus using `@opentui/core` imperatively), our whole app becomes JSX: the main screen is a `<box>` tree with a torrent table, each modal (`InputModal`, `SettingsModal`, `FileModal`, `PeerModal`, `TorrentLimitModal` from `tui.py`) becomes a Solid component conditionally mounted via `<Show>` (backed by `SlotRenderable`) or via `Portal` (explicitly designed for "modals and tooltips outside of a cropping layout" — a closer semantic match to Textual's `push_screen` than manual show/hide). `useKeyboard`/`usePaste` replace Textual's `BINDINGS`/`on_key` handlers; `useTerminalDimensions`/`onResize` replace Textual's automatic resize handling. The one decision this doc surfaces concretely: since `TextTableRenderable` has no JSX tag in the catalogue, we either call `extend({ table: TextTableRenderable })` ourselves before using `<table>` JSX, or build the torrent list by constructing a `TextTableRenderable` imperatively and mounting it via a ref/`Dynamic`, rather than assuming `<table content={...} />` works out of the box like `<box>`/`<text>` do.
