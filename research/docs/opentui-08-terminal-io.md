# Terminal I/O

## Purpose
The layer that actually talks to the OS terminal and the native library: raw ANSI escape sequences, an in-app debug console overlay, and the runtime-abstraction shims (though currently only functional under the Bun runtime). This is the part of opentui most relevant to confirming the "works on Windows without the Zig toolchain" claim (but requiring Bun).

## Key files
- `packages/core/src/ansi.ts` (22 lines) — `ANSI`: a small constant dictionary of raw escape sequences (alt-screen, cursor move, RGB background, bracketed paste).
- `packages/core/src/console.ts` (1254 lines) — `TerminalConsole`: the built-in in-app console/log overlay (captures `console.*` calls, renders as a toggleable panel).
- `packages/core/src/platform/` — runtime abstraction: `ffi.ts` (784 lines, FFI backend abstraction), `runtime.ts` (152 lines, `sleep`/`stringWidth`/`stripANSI`/`writeFile`/`resolveBundledFilePath` — Bun-fast-path-with-Node-fallback), `runtime-assets.bun.ts`/`runtime-assets.node.ts` (per-runtime native-library path resolution, selected via a package.json `imports` map), `assets.ts`, `worker.ts` (425 lines, cross-runtime Worker abstraction for tree-sitter parsing).
- `packages/core/src/node-assets.ts` / `node-asset-target.ts` — resolves which prebuilt native binary package to load for a given `{platform, arch, libc?}` target.

## How it works
`ANSI` is just string/template constants — `switchToAlternateScreen`/`switchToMainScreen` (`\x1b[?1049h`/`l`), `moveCursor(row,col)`, `setRgbBackground(r,g,b)`, bracketed-paste markers — used by `CliRenderer` (doc 01) for screen-mode transitions; almost everything else (cell drawing, actual frame output) goes through the native Zig renderer instead of hand-built ANSI strings.

`TerminalConsole` (constructed by `CliRenderer` in doc 01, one per renderer) intercepts the real `console.log/info/warn/error/debug` via a `Capture`/`TerminalConsoleCache`, keeps up to 1000 cached log entries with caller-info (parsed from `Error().stack`), and renders them into a real `OptimizedBuffer`-backed overlay panel. Public API: `activate()`/`deactivate()`, `show()`/`hide()`/`toggle()`, `focus()`/`blur()`, `resize(w,h)`, `clear()`, `renderToBuffer(buffer)`, `handleMouse(event)`, `setDebugMode`/`toggleDebugMode`, and a `keyBindings`/`keyAliasMap` setter pair (same `ConsoleKeyBinding` pattern as `Textarea`/`Select`, doc 05). `ConsoleOptions` and env vars (`OTUI_USE_CONSOLE`, `SHOW_CONSOLE`) gate whether capture/overlay run at all — relevant since a torrent client's own logging (rate-limit warnings, tracker errors, etc.) can reuse this overlay instead of us building a separate log pane.

The `platform/` directory is where cross-runtime portability was intended to live. `platform/ffi.ts` defines a `FfiBackend` interface (`dlopen`, `ptr`, `suffix`, `toArrayBuffer`) with two concrete shapes described in its types: a `BunFfiBackend` (using `bun:ffi`'s `JSCallback`/`dlopen`, numeric pointers) and a Node-native backend (`NodeDynamicLibrary`/`NodeFfiLibrary`, bigint pointers, `registerCallback`/`unregisterCallback`). However, **this is currently a Bun-only framework in practice**. Under Node, it tries to `require("node:ffi")`, which is not a real module in any stable Node release, silently falling back to a stub backend that crashes with "OpenTUI native FFI is not available for this runtime yet" as soon as it's used. `platform/runtime.ts` picks `Bun.sleep`/`Bun.stringWidth`/`Bun.stripANSI`/`Bun.write` when `globalThis.Bun` exists, otherwise falling back to portable Node implementations, but the native rendering FFI demands Bun. Any run instructions must use `bun run`, not `node` or `tsx`.

`node-asset-target.ts`'s `NATIVE_FILE_NAMES = {darwin: "libopentui.dylib", linux: "libopentui.so", win32: "opentui.dll"}` and `getNativeAssetDescriptor()` (building a package name like `@opentui/core-win32-x64`) directly confirm the win32 native binary claim from the task brief — `win32` is a first-class target alongside darwin/linux, resolved the same way as the others, with no special-casing that would suggest it's second-tier or unsupported.

## Relevance to our torrent client rebuild
This confirms the practical build/runtime question that gates the whole rewrite: while opentui has a win32-x64 prebuilt native binary (`opentui.dll` via `@opentui/core-win32-x64`), **it requires the Bun runtime to execute**. The Node-FFI backend is broken in practice due to relying on a non-existent `node:ffi` module, so a Node.js-only app cannot run the native rendering pipeline. We must use `bun run` and ensure Bun is installed on the machine. `TerminalConsole` is directly useful as our debug/log surface for things `tui.py` currently has no equivalent for (there's no in-app log viewer in the Python version; errors go to `self.notify(...)` toast messages only) — worth deciding whether we want a dedicated log pane (reusing `TerminalConsole`) in addition to, or instead of, toast-style notifications. `ANSI` constants are not something we're likely to touch directly; screen-mode/alt-screen behavior is what `CliRenderer` (doc 01) already wraps.
