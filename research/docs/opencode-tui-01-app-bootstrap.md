# App Bootstrap

## Purpose
This is the process-level entry point: how the TUI process starts, how it talks to the actual agent server (in-process RPC or HTTP), and the Windows-specific hacks needed to make Ctrl+C and console modes behave correctly under Bun on `cmd.exe`/ConPTY. It's the layer above all UI — no Solid components live here except the root `App()`.

## Key files
- `app.tsx` — `tui()` entry (calls `render()` from `@opentui/solid` with the full provider stack), root `App()` component (global keyboard handling, terminal title, command registration for app-wide actions), `ErrorComponent` (fatal-error fallback UI).
- `worker.ts` — runs in a separate Bun `Worker` thread; owns the actual HTTP `Server`, an SSE event-stream-to-RPC bridge, and exposes `fetch`/`server`/`checkUpgrade`/`reload`/`shutdown` over `Rpc.listen`.
- `attach.ts` — `codemie attach <url>` CLI command: connects the TUI to an already-running remote server instead of spawning a worker.
- `event.ts` — `TuiEvent`: zod-typed bus events (`PromptAppend`, `CommandExecute`, `ToastShow`, `SessionSelect`) that let server-side code (plugins, RPC) drive TUI behavior.
- `thread.ts` — `TuiThreadCommand` (`codemie [project]`, the default command): spawns the `worker.ts` Worker thread, decides HTTP-server-vs-direct-RPC transport, and calls `tui()`.
- `win32.ts` — `win32DisableProcessedInput`, `win32InstallCtrlCGuard`, `win32FlushInputBuffer`: raw Win32 console-mode manipulation via `bun:ffi` + `kernel32.dll`.

## How it works
`thread.ts` is the real `$0` CLI command. It installs the Windows Ctrl+C guard *before anything else* (comment: "before any Worker spawn or async work so the OS cannot kill the process group"), spawns `worker.ts` in a `Worker` thread, wraps it with `Rpc.client()`, and decides transport: if `--port`/`--hostname`/`--mdns` flags are present it starts a real HTTP server via `client.call("server", ...)`; otherwise it uses direct in-process RPC (`createWorkerFetch` turns `fetch()` calls into `client.call("fetch", ...)` round-trips to the worker, and `createEventSource` turns worker-emitted `"event"` messages into an `EventSource`). Either way it calls `tui({ url, fetch, events, args, onExit })`.

`app.tsx`'s `tui()` does: install the win32 Ctrl+C guard again (idempotent), detect dark/light terminal background via OSC 11 query (`getTerminalBackgroundColor`, with a 1s timeout fallback to dark), then call opentui's `render()` with a deeply nested provider tree — `ArgsProvider > ExitProvider > KVProvider > ToastProvider > RouteProvider > SDKProvider > SyncProvider > ThemeProvider > LocalProvider > KeybindProvider > PromptStashProvider > DialogProvider > CommandProvider > FrecencyProvider > PromptHistoryProvider > PromptRefProvider > App`. Render options set `targetFps: 60`, `exitOnCtrlC: false` (win32.ts handles that instead), `useKittyKeyboard: {}`, and a built-in debug console with a `ctrl+y` copy-selection binding.

`App()` itself is thin: it reads `route.data.type` and `<Switch>`es between `<Home />` and `<Session />`, sets the terminal window title reactively based on route/session, wires global `sdk.event.on(...)` handlers (toast show, session select, session deleted, session error, update-available), and calls `command.register(() => [...])` with ~25 app-wide commands (switch session, new session, switch model/agent, toggle MCPs, view status, switch theme, help, exit, toggle debug panel/console, write heap snapshot, suspend terminal, toggle terminal title, toggle animations, toggle diff wrap). `ErrorComponent` is the `<ErrorBoundary>` fallback — it renders a stack trace in a scrollbox and a button that builds a pre-filled GitHub issue URL from the error.

`win32.ts` uses `bun:ffi` to call `kernel32.dll` directly: `win32DisableProcessedInput()` clears `ENABLE_PROCESSED_INPUT` on the stdin console handle so Ctrl+C arrives as a normal keypress instead of a `CTRL_C_EVENT` that would kill the process group; `win32InstallCtrlCGuard()` wraps `stdin.setRawMode` and adds a 100ms polling backstop (`setInterval(enforce, 100)`) because "some runtimes can re-apply console modes on the next tick" and the flag is console-global, not per-process; `win32FlushInputBuffer()` discards queued input on exit so buffered keystrokes/mouse events don't leak into the shell prompt after the TUI exits. All three are no-ops on non-Windows/non-TTY.

## Relevance to our torrent client rebuild
`thread.ts` + `worker.ts` is heavier than we need — we don't have a client/server split, so our entry point collapses to roughly what `app.tsx`'s `tui()` does: detect terminal theme, wrap `@opentui/solid`'s `render()` in an `ErrorBoundary`, and mount a provider stack (probably just Theme/KV/Dialog/Command, since we have no SDK/Sync/session concept). The **win32.ts file is the most directly load-bearing piece for us** — since we're explicitly targeting Windows, we should port `win32DisableProcessedInput`/`win32InstallCtrlCGuard`/`win32FlushInputBuffer` close to verbatim (same `bun:ffi` + `kernel32.dll` approach, same "clear ENABLE_PROCESSED_INPUT so Ctrl+C is a keypress not a CTRL_C_EVENT" reasoning) to avoid the exact class of bug (Ctrl+C killing the whole process group) this file was written to fix. `event.ts`'s pattern — a typed bus of external-triggerable events — is worth copying in miniature for things like "libtorrent alert arrived, toast it" instead of prop-drilling a callback. `ErrorComponent`'s fallback-with-stack-trace-and-copy-button is a good template for our own crash screen (currently `tui.py` likely has no equivalent — worth adding).
