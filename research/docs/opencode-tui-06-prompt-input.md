# Prompt Input

## Purpose
This is the actual multi-line text box users type into — the single most feature-dense component in the app. It owns submit/history/stash, `@file`/`@agent` and `/command` autocomplete, paste handling (images, large-text summarization, SVGs), shell mode, and per-keystroke keybinding configuration.

## Key files
- `component/prompt/index.tsx` — `Prompt`: the textarea itself, submit logic, paste/keydown handling, status bar (agent/model/variant, retry state, interrupt hint).
- `component/prompt/autocomplete.tsx` — `Autocomplete`: the `@`/`/` triggered dropdown (files, agents, MCP resources, slash commands), fuzzy-ranked and frecency-boosted.
- `component/prompt/frecency.tsx` — `useFrecency`: frequency+recency scoring for file autocomplete ranking, persisted to a JSONL file.
- `component/prompt/history.tsx` — `usePromptHistory`: up/down-arrow history navigation through past submitted prompts, persisted to JSONL.
- `component/prompt/stash.tsx` — `usePromptStash`: manual "save this draft for later" stack, persisted to JSONL.
- `component/textarea-keybindings.ts` — maps configured keybind names (`input_move-left`, `input_delete-word-forward`, etc.) onto the opentui `<textarea>`'s native `KeyBinding[]` format.

## How it works
`Prompt` holds its live state in a `createStore<{ prompt: PromptInfo; mode: "normal"|"shell"; extmarkToPartIndex: Map; interrupt: number; placeholder: number }>`. `PromptInfo` (`history.tsx`) is `{ input: string, mode?, parts: (FilePart|AgentPart|TextPart)[] }` — critically, the visible text and the structured "parts" (attached files, @-mentioned agents, pasted-and-summarized text blocks) are kept in sync via **extmarks**: the opentui `<textarea>`'s native support for invisible zero-width range markers anchored to text positions, independent of the plain-text content. Each attached file/agent/paste gets an extmark (`input.extmarks.create({start, end, virtual, styleId, typeId})`) mapped to a `parts` array index via `extmarkToPartIndex`; `syncExtmarksWithPromptParts()` re-reads all extmarks after every content change and rebuilds `parts` from wherever they now sit (handles the user editing/deleting text around an attachment without desyncing it), while `restoreExtmarksFromParts()` does the reverse (recreate extmarks when a `PromptInfo` is loaded from history/stash/fork). This extmark-as-source-of-truth-for-attachments pattern is the trickiest part of the whole file.

`submit()` is a plain async function (not itself a command — it's *called by* the `prompt.submit` command and by the textarea's native `onSubmit`): guards on empty input/disabled/autocomplete-open, special-cases bare `exit`/`quit`/`:q` to call the app's `exit()`, requires a valid model (else shows a toast and opens the provider-connect dialog), lazily creates a session if none exists yet, expands any pasted-text extmarks back to their full content inline before sending (attachments stay as separate `parts`, not inlined), then branches three ways: `mode === "shell"` → `sdk.client.session.shell()`; input starts with a recognized `/command` → `sdk.client.session.command()` with args split from the first line only (multi-line content after the command name is preserved as an argument); otherwise → `sdk.client.session.prompt()` with a text part + any file parts. After sending it appends to history, clears the textarea/store, and (if this was the home screen, no `sessionID` prop yet) navigates to the new session after a 50ms `setTimeout` "hack to make sure the message is sent" (their own comment — an acknowledged race-condition workaround, not a clean design).

Paste handling (`onPaste`) is layered: normalize CRLF/CR to LF first (Windows ConPTY quirk called out explicitly in a comment); trim wrapping single-quotes and escaped spaces (shell-drag-and-drop artifact); if the trimmed content looks like a local file path, detect mime type and handle SVG specially (read as text, treat as a pseudo-image attachment) and real images specially (base64-encode, attach as a `FilePart` with a `[Image N]` virtual-text placeholder); otherwise, if the pasted text is ≥3 lines or >150 chars, don't inline it — replace it with a `[Pasted ~N lines]` extmark-backed placeholder part (expanded back to full text only at submit time), keeping the visible textarea uncluttered. Clipboard image reads happen via a custom keydown intercept on `ctrl+v` (`Clipboard.read()`, doc 08) rather than relying on terminal paste, specifically because "Windows terminal doesn't properly send image data through bracketed paste" (comment in the code).

`Autocomplete` is triggered by typing `@` (only if preceded by whitespace/start-of-line) or `/` (only at cursor position 0), tracked as `store.visible: false | "@" | "/"`. For `@`, the option list is agents (non-hidden, non-primary) + files (from `sdk.client.find.files`, sorted by frecency-then-depth-then-alphabetical) + MCP resources; for `/`, it's `command.slashes()` (every registered command with a `slash` field, from doc 04) plus server-provided custom commands. When there's a search string, everything funnels through one `fuzzysort.go()` call across `[value-or-display, description, aliases]` with a custom `scoreFn` that doubles the score for prefix matches and multiplies by `(1 + frecencyScore)` — so recently/frequently used files rank above textually-better matches. Selecting a file inserts `@path` as an extmark (same mechanism as the paste attachments) and calls `frecency.updateFrecency(path)`. A supporting feature: `file.txt#42` or `#42-58` syntax (`extractLineRange`) lets users reference specific line ranges, encoded into the resulting URL's query params.

`frecency.tsx`, `history.tsx`, `stash.tsx` are near-identical in shape: a `createSimpleContext` whose `init()` loads a `.jsonl` file line-by-line on mount (tolerating and dropping corrupt lines — "self-heal corruption" per a comment, rewriting the file with only valid entries), keeps live state in a `createStore`, and appends new entries via `fs/promises`' `appendFile` (fast path) or rewrites the whole file when trimming to a max size (`MAX_HISTORY_ENTRIES=50`, `MAX_STASH_ENTRIES=50`, `MAX_FRECENCY_ENTRIES=1000`). Frecency score is `frequency * (1 / (1 + daysSinceLastOpen))` — pure recency decay, no half-life tuning. History navigation (`move(direction, currentInput)`) only continues walking history if the textarea content still matches what's expected at the current history index — editing the input resets navigation.

`textarea-keybindings.ts` is a small adapter: a fixed list of ~30 semantic action names (`move-left`, `delete-word-forward`, `select-buffer-end`, etc.) each mapped to a `input_<action_with_underscores>` config key, resolved against the user's parsed keybind config, and flattened into the opentui `<textarea>`'s native `keyBindings: KeyBinding[]` prop (plus two hardcoded defaults: bare Enter submits, Meta+Enter inserts a newline).

## Relevance to our torrent client rebuild
Our prompt-input surface is far smaller (magnet-link/path input, maybe a filter box), so most of this is over-scoped for us — but three pieces are worth deliberately borrowing rather than the whole file. First, if our `InputModal` ever needs anything beyond a single-line field (e.g. pasting a magnet link that might have trailing whitespace/quotes), the paste-normalization logic (CRLF handling, quote-trimming) is a real Windows-clipboard gotcha worth copying defensively. Second, `component/prompt/history.tsx`'s JSONL-with-self-healing pattern is a good template for persisting "recently added magnet links" or "recent save-to directories" — simple, crash-tolerant, no real database needed. Third, and most relevant: their `/command` autocomplete (triggered by `/` at position 0, ranked via `fuzzysort`, sourced from `command.slashes()`) is exactly the mechanism we'd want if we ever let users type `/add-magnet` directly into a filter/command box instead of only opening the palette via keybind — it reuses the same command registry from doc 04 rather than maintaining a separate command list. `textarea-keybindings.ts`'s "config key name → native keybinding array" adapter is a clean pattern if we want our text inputs' keybindings (word-delete, line-home, etc.) to be user-configurable rather than hardcoded, though this may be more configurability than a torrent client needs on day one.
