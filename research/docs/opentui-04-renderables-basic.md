# Renderables — Basic

## Purpose
The primitive, always-needed building blocks: a bordered/colored container (`Box`, the closest analogue to Textual's `Container`/`Static` with CSS borders), styled text with nested spans (`Text`/`TextNode`), and a raw pixel-buffer canvas for custom drawing (`FrameBuffer`). Every higher-level widget in the framework (table, input, markdown, etc.) is ultimately composed from these plus `TextBufferRenderable` (doc 03).

## Key files
- `packages/core/src/renderables/Box.ts` — `BoxRenderable`: bordered/filled flex container.
- `packages/core/src/renderables/Text.ts` — `TextRenderable`: displays a `StyledText`/string, extends `TextBufferRenderable` (doc 03).
- `packages/core/src/renderables/TextNode.ts` — `TextNodeRenderable`/`RootTextNodeRenderable`: a lightweight tree of styled spans (fg/bg/attributes/link) that compose into one `Text`'s content — this is how nested styled runs (e.g. `<text>bold <b>word</b> plain</text>`-style composition) work in JSX/imperative code.
- `packages/core/src/renderables/FrameBuffer.ts` — `FrameBufferRenderable`: owns a private `OptimizedBuffer` (doc 01) sized to its own dimensions and blits it into the parent buffer each frame — the escape hatch for custom pixel-level drawing.
- `packages/core/src/renderables/index.ts` — the full renderable-package barrel: re-exports every renderable in `packages/core/src/renderables/*` (Box, Code, Diff, EditBufferRenderable, FrameBuffer, Input, LineNumberRenderable, Markdown, ScrollBar, ScrollBox, Select, Slider, TextTable, TabSelect, Text, TextBufferRenderable, TextNode, Textarea, ASCIIFont, plus `composition/*` helpers) — this is the actual public widget-registration surface of `@opentui/core`.

## How it works
`BoxRenderable extends Renderable`. `BoxOptions` covers `backgroundColor`, `border: boolean | BorderSides[]` (`BorderSides` = `"top"|"right"|"bottom"|"left"`), `borderStyle: BorderStyle` (parsed via `parseBorderStyle`, e.g. `"single"` default), `borderColor`/`focusedBorderColor` (auto-swaps when the box or a focused descendant has focus — `hasFocusWithin` check in `renderSelf`), `title`/`titleAlignment`/`bottomTitle`/`bottomTitleAlignment`, `customBorderChars`, `shouldFill`, and `gap`/`rowGap`/`columnGap` (mapped straight to Yoga's `Gutter` enum, doc 02). `renderSelf(buffer)` skips the native `buffer.drawBox(...)` call entirely when the box has neither a border nor a visible fill — a real perf detail (pure layout wrapper boxes cost nothing at render time). Border edges are additionally pushed into the Yoga node itself (`applyYogaBorders` calls `yogaNode.setBorder(edge, 1|0)`) so border thickness participates in layout sizing, and `getScissorRect()` insets the clip rect by 1 per bordered side so children don't draw over the border.

`TextRenderable extends TextBufferRenderable` (doc 03). Constructor takes `content?: StyledText | string` (plain strings are auto-converted via `stringToStyledText`). It maintains a parallel `rootTextNode: RootTextNodeRenderable` tree — `add()`/`remove()`/`insertBefeore()` on a `TextRenderable` actually delegate to `rootTextNode`, letting you build text out of nested `TextNodeRenderable` children with per-span `fg`/`bg`/`attributes`/`link`, and on each lifecycle pass (`onLifecyclePass`) the tree is flattened back into one `StyledText` via `gatherWithInheritedStyle` and pushed into the underlying `TextBuffer`. Setting `.content` directly bypasses the node tree (`_hasManualStyledText` flag) for the simple string/StyledText case.

`FrameBufferRenderable extends Renderable` is the simplest of the four: it just owns an `OptimizedBuffer` sized `(width, height)`, resizes it in `onResize`, and each frame calls `buffer.drawFrameBuffer(this.x, this.y, this.frameBuffer)` to composite it into its parent. Nothing else manages its pixels — a subclass or external code writes into `frameBuffer` directly using the low-level `OptimizedBuffer` API from doc 01 (this is the pattern used for ASCII-art text (doc 07) and anything needing free-form cell drawing, e.g. a custom sparkline or progress-bar glyph we might want for per-torrent progress bars beyond a plain percentage string).

## Relevance to our torrent client rebuild
`BoxRenderable` directly replaces every bordered container in `tui.py`'s modal `DEFAULT_CSS` (`border: round $accent; padding: 1 2; background: $surface`) — `InputModal`, `SettingsModal`, `FileModal`, `PeerModal`, `TorrentLimitModal`, `TorrentLimitModal` all become a `Box` with `border`, `borderColor`, `padding`, `backgroundColor` props, laid out via the flex properties from doc 02 instead of a CSS block. `TextRenderable` replaces the `Static`/`Label` widgets used for prompts, status text, and the `"⇄ vitorrent  press / for commands"` logo line — its span-based styling (`TextNodeRenderable`'s per-chunk fg/bg/attributes) is actually a closer match to Textual's `markup=True` Rich-markup strings than plain `console.log`-style text would be. `FrameBufferRenderable` is the one component here without a direct Textual equivalent already in use — it becomes relevant only if we want a hand-drawn per-torrent progress bar (block characters colored by percentage) instead of the current plain `f"{progress*100:.1f}%"` string cell, or for the ASCII-art logo idea (doc 07 covers the purpose-built `ASCIIFont` renderable, which is likely a better fit than hand-rolling one on `FrameBuffer`).
