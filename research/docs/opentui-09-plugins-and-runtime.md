# Plugins and Runtime

## Purpose
Two unrelated-but-adjacent systems bundled under this name: (1) a Bun-bundler-only mechanism that lets externally-loaded plugin code share the host app's single `@opentui/core`/`solid-js` module instances instead of bundling its own duplicate copies, and (2) a genuinely generic "slot" plugin architecture (register a named extension point, plugins contribute renderers into it, ordered/first-wins/append-composed) that is how apps like OpenCode let third-party plugins inject UI into fixed places (status bar, sidebar, etc.). `syntax-style.ts` (theme/highlight color definitions) is unrelated to both but was grouped here as it's plumbing consumed by the plugin/runtime-module system's `RenderLib` handle pattern.

## Key files
- `packages/core/src/runtime-plugin.ts` (626 lines) — `createRuntimePlugin()`: a `BunPlugin` (Bun's bundler plugin API) that rewrites `@opentui/core`/`@opentui/solid`/`solid-js` imports inside externally-loaded plugin code to virtual `opentui:runtime-module:*` module ids resolving to the host's already-loaded instances — prevents "two copies of solid-js" class-identity bugs in a plugin system.
- `packages/core/src/runtime-plugin-support.ts` (13 lines) / `runtime-plugin-support-configure.ts` (63 lines) — a thin, idempotent-install wrapper around `createRuntimePlugin` (`ensureRuntimePluginSupport()`, global-flag-guarded so it's safe to call from multiple places without double-registering the Bun plugin).
- `packages/core/src/plugins/types.ts` — the plugin-system's core types: `Plugin<TNode,TSlots,TContext>`, `SlotRenderer`, `SlotMode = "append"|"replace"|"single_winner"`, `PluginErrorEvent`.
- `packages/core/src/plugins/registry.ts` (402 lines) — `SlotRegistry`/`createSlotRegistry()`: the runtime registry plugins call `register()` on; resolves all renderers contributed to a given slot name, tracks per-plugin errors, supports ordering and hot re-registration.
- `packages/core/src/plugins/core-slot.ts` (579 lines) — `createCoreSlotRegistry`/`registerCorePlugin`/`resolveCoreSlot`/`SlotRenderable`: the opentui-core-specific instantiation of the generic registry (bound to `Renderable`-shaped nodes), plus a `SlotRenderable` component that renders "whatever plugins contributed to this slot" directly into the tree.
- `packages/core/src/syntax-style.ts` (274 lines) — `SyntaxStyle`/`StyleDefinition`/`convertThemeToStyles()`: native-backed named-scope-to-color/attribute style table, consumed by `TextBuffer.setSyntaxStyle()` (doc 03) and `CodeRenderable` (doc 07).

## How it works
`createRuntimePlugin(options: CreateRuntimePluginOptions)` returns a `BunPlugin` whose `setup(build)` hooks `onResolve`/`onLoad`/`build.module()`. For the default `core: "@opentui/core"` (plus `"@opentui/core/testing"`) plus any `additional` entries, it registers a virtual module id (`opentui:runtime-module:<encoded-specifier>`) resolving to the *host's* already-imported module object, then rewrites matching `import`/`require` specifiers inside plugin source files (own files rewritten eagerly; `node_modules` files only if ESM and actually reachable from a runtime-module import, tracked via a recursive reachability scan) to point at that virtual id instead of re-resolving/re-bundling the real package. The file's own comments explain the non-obvious constraints driving this: Bun can break CJS/UMD interop if arbitrary files are routed through `onLoad`, `onResolve` must stay synchronous, and Bun sometimes native-loads `node_modules` ESM without firing `onResolve` at all — so the implementation prescans reachability rather than doing a blanket rewrite. `ensureRuntimePluginSupport()` is the idempotent, globally-flagged installer apps actually call (checks a `globalThis` flag before calling Bun's real `plugin()` registration, throwing if called twice with incompatible options).

`plugins/registry.ts`'s `SlotRegistry<TNode,TSlots,TContext>` is generic over the rendered node type, the map of slot-name→props-type, and a context type. `register(plugin)` adds a `Plugin` (has `id`, optional `order`, optional `setup(ctx,renderer)`/`dispose()`, and a `slots` map of slot-name→`SlotRenderer` function) and returns an unregister callback. `resolve(slotName)`/`resolveEntries(slotName)` return the ordered list of renderer functions contributed to that slot by all registered plugins (respecting `order` and the slot's `SlotMode`: `"append"` = show all contributions, `"replace"`/`"single_winner"` = only the winning one). Errors thrown by a plugin's `setup`/render are caught and reported via `reportPluginError`/`onPluginError(listener)` rather than crashing the render loop — `PluginErrorEvent` carries `pluginId`, `slot`, `phase` (`"setup"|"render"|"dispose"|"error_placeholder"`), and the error itself.

`plugins/core-slot.ts` specializes this for opentui: `createCoreSlotRegistry()` binds `TNode` to whatever opentui renders, `registerCorePlugin()` is the app-facing registration call, and `SlotRenderable` (a real `Renderable` subclass) is dropped into your tree wherever you want "whatever plugins have contributed here" to actually appear — e.g. a fixed status-bar `Box` that yields a `<SlotRenderable slot="statusbar-right">` and any installed plugin can inject its own widget there without the host app knowing about it ahead of time. This is genuinely the same mechanism `packages/solid/examples/components/plugin-slots-demo.tsx` and `external-plugin-slots-demo.tsx` exercise (seen in the directory listing for doc 10's Solid package).

`SyntaxStyle` (native-backed, `SyntaxStyle.create()`) is a name→`{fg,bg,bold,italic,underline,dim}` map with an internal merge/name cache; `convertThemeToStyles(theme: ThemeTokenStyle[])` converts a TextMate/VSCode-shaped theme (`{scope: string[], style: {...}}[]`) into opentui's flat `Record<string, StyleDefinition>` — this is the theme-ingestion path for syntax highlighting (doc 07's `Code`/`Diff`/`Markdown` code blocks), not something a plain data-display app needs to touch directly.

## Relevance to our torrent client rebuild
Almost none of this is on our critical path — we are not building a plugin-extensible app, not loading third-party plugin code via Bun's bundler, and not doing syntax highlighting. `runtime-plugin.ts`/`runtime-plugin-support*.ts` are entirely irrelevant unless we later decide our torrent client itself should support third-party plugins (e.g. a community plugin adding a new tracker-stats panel) — worth remembering this mechanism exists (and that it's Bun-bundler-specific, so it wouldn't transfer if we build/ship with a different bundler) if that need ever arises, rather than reinventing it. The `plugins/registry.ts`/`core-slot.ts` slot system is the one piece with plausible long-term relevance: if we want our own settings modal or status bar to be extensible later (e.g. letting a user-installed script add a custom column to the torrent table), this is the exact mechanism to reuse rather than build a bespoke one. For the v1 rebuild scoped against `tui.py`/`session.py`, this whole doc is background knowledge, not implementation surface.
