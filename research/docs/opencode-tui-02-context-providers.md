# Context Providers

## Purpose
This is the app's entire state-management layer: a SolidJS context per concern (routing, theme, keybinds, sync'd server data, local prefs), each built on the same tiny factory so every provider/hook pair looks and behaves identically. There is no Redux/Zustand/MobX — it's all native `solid-js` primitives (`createSignal`, `createStore`, `createMemo`, `createContext`).

## Key files
- `context/helper.tsx` — `createSimpleContext()`: the factory every other context in the app is built from.
- `context/args.tsx` — CLI-arg passthrough (`--model`, `--agent`, `--prompt`, etc.) as a context.
- `context/directory.ts` — derives the "cwd:branch" string shown in header/footer from sync data.
- `context/exit.tsx` — the app's exit function, wrapped with a settable "exit message" (printed to stdout after teardown).
- `context/keybind.tsx` — parses/matches configured keybindings against key events; owns the leader-key (`ctrl+x`) state machine.
- `context/kv.tsx` — a tiny persisted key-value store (JSON file) for UI prefs (feature toggles, sidebar state, etc.).
- `context/local.tsx` — client-local (not server-synced) state: current agent, current model + favorites/recents/variants, MCP enable/disable.
- `context/prompt.tsx` — holds a mutable ref to the currently-mounted prompt textarea component.
- `context/route.tsx` — the "router": a `createStore` holding either `{type:"home"}` or `{type:"session", sessionID}`.
- `context/sdk.tsx` — wraps the generated API client, subscribes to SSE (or a direct `EventSource`), and re-emits events through a global emitter, batched every 16ms.
- `context/sync.tsx` — the big one: mirrors all server state (sessions, messages, providers, permissions, MCP status, etc.) into one `createStore`, kept live via the SDK's event stream.
- `context/theme.tsx` — loads ~30 bundled theme JSON files, resolves color refs/light-dark variants into `RGBA`, and can synthesize a theme from the terminal's actual ANSI palette.

## How it works
`createSimpleContext({ name, init })` (in `helper.tsx`) is the pattern: `init` is a function that runs once per provider mount (it can call other hooks like `useSync()` internally, since it executes inside the Solid component), and its return value becomes the context value. The returned `{ use, provider }` pair gives you a hook that throws if called outside its provider, and a `provider` component. One subtlety: if `init()`'s return value has a `ready` property, the provider won't render `children` until `ready === true` — used by `theme.tsx` and `kv.tsx` to gate rendering until an async file load resolves. State internally is either a plain closure variable (`exit.tsx`'s `message`), a `createSignal` (`kv.tsx`'s per-key signals), or a `createStore` (`sync.tsx`, `local.tsx`, `theme.tsx` — anything with nested/keyed data).

`sync.tsx` is the architectural center: it holds one big `createStore` shaped like the server's whole data model (sessions, messages, parts, permissions, questions, todos, MCP/LSP status, providers, config, vcs info) and a `bootstrap()` function that does a staged fetch — blocking requests (providers, agents, config) resolve first and flip `status` to `"partial"`, then a second wave (commands, LSP, MCP, formatters, session status) resolves and flips `status` to `"complete"`. After bootstrap, `sdk.event.listen()` patches the store incrementally per event type (`session.updated`, `message.part.delta` appends to a string field, etc.) using `Binary.search` for O(log n) lookups into sorted arrays and `reconcile()`/`produce()` from `solid-js/store` for fine-grained updates (Solid's store diffing needs `reconcile` for replaced objects vs `produce` for in-place mutation). Message lists are capped at 100 entries (oldest dropped) to bound memory.

`local.tsx` layers on top of `sync`: `agent.current()`/`agent.set()`/`agent.move()` cycle through non-subagent agents; `model.current` is a `createMemo` chain that tries, in order, the per-agent override, the agent's configured model, then a `fallbackModel` memo (CLI arg → config → most-recent-valid → provider's first model) — all gated through `isModelValid()` so a stale/removed model never gets selected. Recents/favorites persist to `~/.local/state/.../model.json` via `Filesystem.writeJson`, deduped with `uniqueBy` and capped at 10.

`theme.tsx` bundles ~30 theme JSON files as ES imports (`with { type: "json" }`), each a `{ defs, theme }` shape where color values can be a hex string, a ref to another key, a `{dark, light}` variant object, or an ANSI code number; `resolveTheme()` recursively resolves refs into `RGBA` and computes derived values (`selectedListItemText` falls back to `background`, `backgroundMenu` falls back to `backgroundElement`). A `"system"` pseudo-theme is synthesized on demand from `renderer.getPalette()` (the actual terminal's 16-color ANSI palette), generating a grayscale ramp and diff colors by luminance math (`generateGrayScale`, `generateMutedTextColor`). The context also builds two `SyntaxStyle` instances (full + a "subtle" one with `thinkingOpacity`-scaled alpha) used for markdown/code rendering — not relevant to us, but the general "derive N related color scales from one base theme" technique is.

`keybind.tsx` parses `sync.data.config.keybinds` (a user-config record) into `Keybind.Info[]` per action name via `Keybind.parse`, and exposes `match(key, evt)` for components to check "did this keypress match the configured binding for X". It separately implements the leader-key UX: pressing the configured leader sets `store.leader = true`, blurs the currently focused element (so keystrokes don't leak into a textarea), starts a 2s timeout, and any subsequent keypress or the timeout resets it and restores focus.

A component reads global state by calling the corresponding hook — e.g. `const { theme } = useTheme()`, `const sync = useSync()`, `const keybind = useKeybind()` — no prop drilling, no selector/connect wrapper. Since these are plain Solid contexts, reactivity is automatic: reading `theme.text` or `sync.data.session` inside a `createMemo`/JSX expression subscribes that computation to changes.

## Relevance to our torrent client rebuild
`createSimpleContext()` is worth copying close to verbatim — it's ~15 lines and gives us the "hook throws outside provider" safety plus the optional `ready`-gating for free. We'd want a `context/torrent.tsx` shaped like `sync.tsx`: one `createStore` mirroring libtorrent's session state (torrent list, per-torrent status, peers, files), fed by whatever IPC/polling mechanism replaces their SSE event stream — the same incremental-patch pattern (`reconcile`/`produce` keyed by torrent info-hash instead of message ID) applies directly. `context/local.tsx`'s "current selection + recents, validated against live server data" pattern maps onto things like "last-used save directory" or "most recent trackers" in our `InputModal`/`SettingsModal`. `context/theme.tsx` is far more elaborate than we need (we likely want 2-3 fixed themes, not 30 externally-loaded ones with light/dark variant resolution), but the RGBA-based theme-object-as-context approach is exactly what should replace Textual's CSS-string `Theme` object. `context/keybind.tsx`'s leader-key state machine is directly reusable if we ever want a `ctrl+x` style prefix key instead of (or in addition to) our current slash-command palette.
