# Text Rendering

## Purpose
Terminal UIs need more than "draw a string" — wrapping, scrolling, selection, syntax highlighting, and cursor-editing all operate on the same underlying text data. opentui splits this into a native rope-like buffer holding the raw styled text, a "view" that projects it (wrap/viewport/scroll/selection) without copying, and an editable variant for input widgets. This mirrors why Textual has both `Static`/`RichLog` (display-only) and `Input`/`TextArea` (editable) built on different internal representations.

## Key files
- `packages/core/src/text-buffer.ts` — `TextBuffer`: native-backed store for read-only/styled text (plain `setText`, `append`, `loadFile`, or `setStyledText(StyledText)` with per-chunk fg/bg/attributes/links), plus highlight ranges and syntax-style attachment.
- `packages/core/src/text-buffer-view.ts` — `TextBufferView`: a view over a `TextBuffer` with its own wrap width/mode, viewport, scroll, and selection state; multiple views can project the same buffer differently.
- `packages/core/src/renderables/TextBufferRenderable.ts` (504 lines) — `TextBufferRenderable` abstract class: the `Renderable` base for any widget that displays a `TextBuffer`+`TextBufferView` pair (scrolling, mouse-selection wiring, viewport sync with layout size). `Text.ts` and `Code.ts` extend this.
- `packages/core/src/edit-buffer.ts` — `EditBuffer`: the editable counterpart — cursor motion (`moveCursorLeft/Right/Up/Down`), text mutation (`insertChar`, `deleteChar`, `deleteRange`, `newLine`), undo/redo, word-boundary navigation, all backed by native rope storage.
- `packages/core/src/editor-view.ts` — `EditorView`: the view layer over an `EditBuffer`, analogous to `TextBufferView` but with cursor/viewport concerns added (`getVisualCursor`, `moveUpVisual/DownVisual`, `setScrollMargin`, placeholder text).
- `packages/core/src/NativeSpanFeed.ts` (375 lines) — a separate, lower-level primitive: a zero-copy byte-stream wrapper over native Zig memory used to pipe rendered frame bytes to a custom `stdout` (see `CliRenderer`'s feed wiring in doc 01) — not part of the text-editing story, despite living near these files.

## How it works
`TextBuffer.create(widthMethod)` allocates native storage; `setText(text: string)` or `setStyledText(text: StyledText)` (chunks: `{text, fg?, bg?, attributes?, link?}`) fills it. Highlights are separate from styled chunks: `addHighlightByCharRange({start,end,styleId,...})` (absolute char offsets) or `addHighlight(lineIdx, highlight)` (column offsets within a line) — used for things like search-match or diagnostic highlighting layered on top of base styling. `setSyntaxStyle(style: SyntaxStyle | null)` attaches a `SyntaxStyle` (doc 09/`Code.ts`, doc 07) for tree-sitter-driven coloring.

`TextBufferView.create(textBuffer)` wraps a buffer for display: `setWrapWidth(n)`/`setWrapMode("none"|"char"|"word")` control reflow, `setViewport(x,y,w,h)`/`setViewportSize(w,h)` control the visible window, `lineInfo`/`logicalLineInfo` (getters returning `LineInfo` from doc 02) expose wrapped-line metrics for scrollbar math, and `setSelection`/`setLocalSelection` (screen-coordinate variant) drive text selection highlighting independent of the buffer's own highlights.

`TextBufferRenderable` (abstract `Renderable`) is what actual widgets extend: its constructor creates its own private `TextBuffer`+`TextBufferView` pair sized to `RenderContext.widthMethod`, wires mouse-scroll handling (`handleScroll` adjusts `scrollX`/`scrollY` with clamping against `scrollWidth`/`scrollHeight` = `lineInfo.lineWidthColsMax`/line count), and implements `LineInfoProvider` (from doc 02's `types.ts`) so scrollbars (doc 06) can read `lineInfo`/`lineCount`/`virtualLineCount`/`scrollY` generically. `TextBufferOptions` (constructor options) covers `fg`/`bg`/`selectionBg`/`selectionFg`/`selectable`/`attributes`/`wrapMode`/`tabIndicator`/`truncate`.

`EditBuffer` is the editable-text native store: mutation methods (`insertChar`, `insertText`, `deleteChar`/`deleteCharBackward`, `deleteRange(startLine,startCol,endLine,endCol)`, `newLine`, `deleteLine`), cursor methods (`moveCursorLeft/Right/Up/Down`, `gotoLine`, `setCursor(line,col)`, `getCursorPosition()`, `getNextWordBoundary()`/`getPrevWordBoundary()`), and `undo()`/`redo()`/`canUndo()`/`canRedo()`. `EditorView` layers viewport/visual-cursor concerns on top (`getVisualCursor()`, `moveUpVisual/DownVisual`, `setPlaceholderStyledText` for empty-state hint text, `setScrollMargin`) — this is what backs `Input`/`Textarea` (doc 05).

## Relevance to our torrent client rebuild
Nearly all our display text is simple and static per refresh tick (torrent name, progress %, rates, state icon) — that's a plain `Text`/`TextBufferRenderable` with `setText()` called once per second from the refresh loop, no wrapping or editing needed, directly replacing Textual `Static`/`DataTable` cell strings. The one place this doc's deeper machinery matters is the add-magnet/settings text inputs (today's `Input(id="value", value=self.initial)` in `InputModal`/`SettingsModal`) — those map to `EditBuffer`/`EditorView` via the `Input`/`Textarea` renderables (doc 05), which is where cursor motion, undo, and placeholder text (e.g. "magnet:?xt=..." hint) come from for free instead of us hand-rolling cursor state like the current Python code implicitly gets from Textual's `Input` widget. Peer/file lists that could grow long (many peers, many files in a multi-file torrent) are candidates for `TextBufferView`'s scroll/viewport support if we don't just use `TextTable`/`ScrollBox` (docs 06) directly.
