# Routing and Screens

## Purpose
This is the "screen" layer: a two-route router (home / session), and the session screen's header, footer, and sidebar chrome that surrounds the actual message-list content. It's the closest analogue to our torrent-list table + status bar + peers/files panels.

## Key files
- `routes/home.tsx` — the landing screen: big logo, prompt box, tips, first-run MCP hint, bottom status bar.
- `routes/session/index.tsx` — the session screen (huge file, ~2200 lines): message list, per-message-type renderers, ~35 session-scoped commands, sidebar/header visibility logic.
- `routes/session/header.tsx` — top bar inside a session: title, token/cost usage, subagent parent/prev/next nav.
- `routes/session/footer.tsx` — bottom bar inside a session: cwd, MCP/LSP/permission counts, a delayed "get started" hint.
- `routes/session/sidebar.tsx` — collapsible right-hand panel: session stats, MCP/LSP status, todo list, modified-files diff summary.
- `routes/session/permission.tsx` — full-width inline prompt for tool-permission requests (allow once/always/reject), with a diff viewer for edits.
- `routes/session/question.tsx` — tabbed inline prompt for agent-asked questions (single/multi-select + free text per tab).
- `routes/session/dialog-message.tsx`, `dialog-timeline.tsx`, `dialog-subagent.tsx`, `dialog-fork-from-timeline.tsx` — small `DialogSelect`-based action menus scoped to a message/session.

## How it works
Routing (`context/route.tsx`, covered in doc 02) is a two-variant discriminated union in a `createStore`; `App()` in `app.tsx` just `<Switch>`es on `route.data.type`. There's no route stack, no nested routes, no URL — `navigate()` replaces the whole route object. "Modal-like" navigation (drilling into a message, forking, viewing timeline) is handled entirely by the dialog system (doc 04/05), not by routing.

`routes/session/index.tsx` establishes a Solid `context.Provider` (a *second*, screen-local context, separate from the doc-02 global ones) carrying `{ width, sessionID, conceal, showThinking, showTimestamps, showDetails, showGenericToolOutput, diffWrapMode, sync }` — this is how deeply nested message/tool sub-components (defined in the same file) read session-scoped display prefs without prop drilling through every intermediate component. Most of these prefs are `kv.signal(...)`-backed (persisted). The screen registers ~35 commands via `command.register()` covering session lifecycle (share, rename, fork, compact, undo/redo, export), display toggles (conceal, timestamps, thinking, tool details, header/sidebar visibility), and scroll navigation (page/half-page/line up-down, first/last message, next/prev message — the last two walk the rendered `scrollbox`'s children by `.y` position, not by data index). The message list itself is a `<For each={messages()}>` inside a `<scrollbox stickyScroll stickyStart="bottom">`, switching per message on `role` (`UserMessage`/`AssistantMessage` components defined lower in the same file) and, within assistant messages, per-part on `part.type` via a `PART_MAPPING` object (`text`/`tool`/`reasoning` → component) rendered with `<Dynamic>`. Tool parts fan out further by `part.tool` name (bash/read/write/edit/grep/glob/task/etc.) into ~15 dedicated renderer components, all sharing two layout primitives: `InlineTool` (single-line, icon + label, used for read/glob/etc.) and `BlockTool` (bordered box with a title bar, used for bash output, diffs, generic fallback).

`header.tsx` is a `<Switch>` on whether the session has a `parentID` (subagent): if so it shows "Subagent session" + Parent/Prev/Next nav buttons (each just `command.trigger("session.parent"|"session.child.previous"|"session.child.next")`); otherwise the plain title + token-count/cost. Token count is computed by finding the last assistant message with `tokens.output > 0` and summing `input+output+reasoning+cache.read+cache.write`, shown as a percentage of the model's context limit if known. `footer.tsx` shows cwd + a `Switch` between a one-time "Get started /connect" welcome hint (shown/hidden on a 10s→5s→10s... `setTimeout` cycle, only while disconnected) and, once connected, live counts (permissions pending, LSP servers, MCP servers) each as a colored bullet + label — clicking any of it isn't wired, they're just status text with a `/status` hint.

`sidebar.tsx` is the most structurally relevant file for us: a fixed-width (`42`) panel, `position="absolute"` when overlaid on narrow terminals vs `"relative"` when docked on wide ones (`dimensions().width > 120` in `index.tsx`), containing independently-collapsible sections (MCP, LSP, Todo, Modified Files) each following the same pattern — a clickable header row with a `▼`/`▶` disclosure triangle (only shown if more than 2 items) toggling a `createStore`-backed `expanded.<section>` boolean, then a `<Show>`-gated list. Each section aggregates from `sync.data.*` (already covered in doc 02) and is purely presentational.

`permission.tsx` and `question.tsx` are not dialogs (not in the `DialogProvider` stack) — they render inline, replacing the prompt input, driven by whether `sync.data.permission[sessionID]`/`sync.data.question[sessionID]` arrays are non-empty (checked in `index.tsx`'s render, `<Show when={permissions().length > 0}><PermissionPrompt .../></Show>`). `PermissionPrompt` has a 3-stage local state machine (`"permission" | "always" | "reject"`) and a big `info()` function that switch-cases on `permission` type (edit/read/glob/grep/bash/task/webfetch/etc.) to pick an icon/title/body — the `edit` case renders an actual `<diff>` opentui component. It also supports a fullscreen-expand mode (`ctrl+f`) via `<Portal>`. `QuestionPrompt` supports multiple questions as tabs, single or multi-select per question, and a free-text "type your own answer" option per question, ending in a synthetic "Confirm" tab when there's more than one question.

The four `dialog-*.tsx` files in `routes/session/` are trivial: each renders a `<DialogSelect>` with 1-3 hardcoded `options`, whose `onSelect` calls an SDK method (revert/fork/copy) or `route.navigate()`. `DialogTimeline`/`DialogForkFromTimeline` build their option list by scanning `sync.data.message[sessionID]` for user messages with real text parts, most-recent-first.

## Relevance to our torrent client rebuild
Our router is even simpler than theirs — likely just one screen (the torrent table) plus modals, so we may not need a `route.tsx` at all; if we do add a second screen (e.g. a dedicated "torrent detail" view), copy the discriminated-union-in-a-store pattern rather than pulling in a routing library. **`header.tsx` and `footer.tsx` map directly**: our header becomes session count / global speed / DHT status instead of title/tokens, our footer becomes the same "cwd-equivalent (download dir) + status bullets" layout — the colored-bullet-plus-count pattern (`• N MCP`, `• N LSP`) is exactly how we'd show "● 3 seeding / 2 downloading" or "⊙ DHT: 40 nodes". **`sidebar.tsx`'s collapsible-section pattern is a strong candidate for our `PeerModal`/`FileModal` content** — instead of separate modals, we could have a single collapsible sidebar with Peers/Files/Trackers sections each independently expandable, using the identical `▼/▶` + `createStore` toggle idiom. The screen-local Solid context in `index.tsx` (session prefs threaded to nested renderers) is the right pattern if our torrent-row components need shared display prefs (show-speed vs show-ETA, compact vs detailed rows) without prop drilling. `permission.tsx`/`question.tsx`'s "inline replaces the input area, not a dialog" approach is worth considering for something like a delete-confirmation-with-diff-of-files-to-remove, though our `TorrentLimitModal`/`InputModal` are probably simple enough to stay as true dialogs (doc 05).
